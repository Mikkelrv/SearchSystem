## Why

Search currently matches query words against indexed words by exact, case-sensitive,
byte-for-byte string equality (`Dictionary<string,int>.ContainsKey` over the raw word,
with the whole vocabulary loaded into memory at startup). Searching `Hello` does not find
documents that contain `hello`, and Unicode text that differs only in normalization form
(composed vs. decomposed accents, full-width vs. ASCII digits) fails to match.

Case-insensitive search is the expected default. This change also moves word resolution
off the in-memory dictionary and onto an indexed database lookup, and reshapes the `word`
table into a normalized-term table — the foundation the planned synonym search and
relevance scoring both build on, and a prerequisite for scaling past ~1M documents.

Separately, the console today returns only the first ten matches. Users need the full set
of documents that contain a query word, so this change also removes the result-count cap.

## What Changes

- **Shared**: add `TextNormalizer` (NFKC normalization + `ToLowerInvariant` case fold) and
  `Tokenizer` (the word-splitting rules, moved out of the crawler so the indexer and the
  case-sensitive search filter tokenize text identically).
- **Schema**: the `word` table becomes **one row per normalized term** (NFKC + case
  folded), with a `UNIQUE` constraint on the term string (which also provides the lookup
  index). `Occ` is unchanged. **BREAKING (schema + data)** — a full re-index is required.
- **Indexer**: tokenize and fold each word via the shared helpers before storing it.
- **ConsoleSearch**: resolve each query word with an indexed SQL lookup
  (`SELECT id FROM word WHERE name = @folded`) instead of loading every word into memory.
- **ConsoleSearch**: match **case-insensitively by default**.
- **ConsoleSearch**: return **every** matching document — under both default and `--case`
  matching — instead of a fixed top-ten page. `SearchLogic.Search` drops its `maxAmount`
  parameter; the caller passes no limit.
- **ConsoleSearch**: accept a `--case` token anywhere in the search input line. When
  present, that one search is case-sensitive; the token is removed from the query words
  and the next line returns to case-insensitive. Case sensitivity is applied as a
  **post-filter** over the ranked results (re-reading the matched source files), so no
  casing data is stored in the index.

## Capabilities

### New Capabilities

- `search-matching`: how ConsoleSearch resolves the words a user types into document
  matches — Unicode normalization, default case-insensitive matching, the per-query
  `--case` opt-out for case-sensitive matching, and returning every matching document.

### Modified Capabilities

(none — no existing spec covers query/word matching or the index schema)

## Impact

- **Code**
  - `Shared/`: new `TextNormalizer`, new `Tokenizer`.
  - `indexer/Crawler.cs`: tokenize + fold via the shared helpers.
  - `indexer/DatabaseSqlite.cs` + `indexer/DatabasePostgres.cs`: `word.name TEXT UNIQUE`;
    words keyed by folded form.
  - `ConsoleSearch/IDatabase.cs` + `DatabaseSqlite.cs` + `DatabasePostgres.cs`:
    `GetWordIds` resolves via SQL; the in-memory word map (`mWords` / `GetAllWords`) is removed.
  - `ConsoleSearch/App.cs`: parse and strip the `--case` token; pass no result-count limit.
  - `ConsoleSearch/SearchLogic.cs`: fold query words; apply the `--case` post-filter;
    drop `maxAmount` and return every ranked match.
- **Data**: existing SQLite / Postgres indexes must be regenerated by re-running the indexer.
- **No new dependencies** — `string.Normalize(NormalizationForm.FormKC)` is in the BCL.
- **Design trade-offs (SOLID / KISS)**:
  - Case-sensitive `--case` re-reads matched source files at query time instead of storing
    per-occurrence casing. This keeps the `Occ` table lean for the planned scoring work.
    Because results are unbounded, this reads every ranked candidate's file on each `--case`
    search — acceptable for this corpus, revisited if measured too slow. Rejected alternative
    (a `surface` column on `Occ`, roughly doubling the largest table) is weighed in `design.md`.
  - Results are unbounded: `Search` returns a `DocumentHit` for every matching document.
    No pagination (YAGNI until the console UI needs it); a broad query prints a long list.
  - The indexer still holds the term dictionary in memory during a batch index run. Not
    addressed here — it is a resumable batch job, not a long-lived process — noted as
    future work in `design.md`.
